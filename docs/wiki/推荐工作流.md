# 推荐的整合包制作工作流

[English](Recommended-Workflow) | [快速开始](快速开始)

把配置修改当作一次小型、可审查的版本发布。文件解析成功只是第一步，实际武器、配方、资源和联机行为仍需验收。

---

## [1] 固定可复现的基线

记录 Minecraft、Forge、Java、SuperbAddon、SuperbWarfare、GeckoLib 和可选兼容模组的版本，同时保留模组列表、数据包、当前 config/superbaddon/ 以及存档备份。建立独立的客户端／服务端测试实例，不要先在正式共享世界里改。

当前源码的构建与运行时版本字符串没有完全对齐，详见[更新日志](更新日志)。测试记录应指定实际 JAR／提交，不要只写“最新版”。

## [2] 写出可观察的要求

有效要求例如：“这个载具使用这份装配材料表”“这种弹药从这个抛壳口生成一个弹壳物品堆”“指定武器限制直击击退，未指定武器保持不变”。

首次测试不要同时混合内容删除、弹药替换、穿透和燃料变化。按[配置总览](配置总览)为每项要求找到所属系统，将玩家操控偏好与服务端玩法配置分开。

## [3] 只发现并采用需要的规则

使用非激活[扫描](抛壳扫描命令)获取 ID 和武器／弹药结构。扫描前把需要长期保留的生成规则移到 custom/，备份放到扫描目录外，并记住普通扫描也会重写输出。

每次只启用一个审查过的候选，明确优先级，缩小目标集合。不同意图优先拆成不同文件或规则；文件名便于组织，真正行为由数值优先级和各功能选择方式决定。

## [4] 先检查语法，再重载正确系统

使用严格 JSON 编辑器或校验器检查文件，确认目标 ID、单位、必需包装格式以及布尔开关位置。不要把文档的编号注释一起复制进 JSON。

按[配置总览](配置总览)的重载表操作。外部规则重载不是配方重载，这些命令也不会下发客户端本地文件。弹药回退、缓存资源或 MTS 配置无法靠窄范围重载可靠恢复时，应重启并核对基线。

## [5] 使用验收矩阵

| 修改 | 正向测试 | 反向／边界测试 |
| --- | --- | --- |
| 抛壳 | 正确枪械、座位和已选弹药 | 未列出武器、其他弹药、满库存、第一个抛壳物品有效 |
| 弹药覆写 | 装填、扣除、开火、退弹 | 被移除弹药、新取武器、联机客户端选择 |
| 击退 | 分别测试直击与爆炸 | 未指定武器、目标抗性、disabled 不带正数 min |
| 穿透 | 固定护甲配置、多个爆炸距离 | 零值／原生回退、创造／队伍限制、不支持的伤害路径 |
| 载具配方 | 界面及实际材料成本 | 组冲突、单体覆写、缺失配方、其他限制来源 |
| 资源裁剪 | 目标入口被正确过滤 | 共享模型、容器／装配台、存档重载、已有方块 |
| MTS | 有效燃料与可接收容量 | 未列出燃料、接近满载、附近多载具、重启后重连 |
| 弹壳合成 | 按指定数量正确扣除 | 分散弹壳堆、数量不足、Shift 合成、自定义自动化 |

这是推荐验收项，不表示本次文档补全已经运行这些游戏测试。修改记录应分别写预期与实际结果。

## [6] 用真实独立服务端验证

安装目标客户端和服务端构建，而不是只开两个单人世界；一致分发相关本地资源／内容配置。测试加入、射击、弹药选择、配方使用，以及重启后重新连接。只有一端报错时应同时检查双端日志。

服务端计算有效不代表客户端界面和资源匹配。MTS 与视角有客户端本地职责，自动合成和伤害事件集成也需要单独验证其真实路径。

## [7] 发布并保留回退

对维护配置进行版本管理，列出依赖变化，记录哪些文件属于客户端、哪些属于服务端。把扫描输出与已批准规则分开。回退说明应在必要时同时恢复配置和持久化存档状态。

维护 Wiki 时，同时更新 docs/wiki/ 中的页面与另一语言对应页，保留历史归档和已有页面地址。执行 `python3 docs/validate_wiki.py`；同步流程也会先检查再进行非破坏性复制。只有检查实际 Actions 结果后，才能断言仓库修改已发布到 GitHub Wiki。
