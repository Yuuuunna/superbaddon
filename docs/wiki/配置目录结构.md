# 配置目录结构

[English](Config-Directory-Structure) | [配置总览](配置总览)

路径属于正在运行的游戏实例，而不是属于某个账号。不同启动器、独立服务端、开发环境的 `run/` 目录，都可能有各自不同的 `config/`。

---

## [1] 实例级配置

```text
<instance>/
├─ mods/
├─ config/
│  └─ superbaddon/
│     ├─ content_control.json
│     ├─ vehicle_recipe_override.json
│     ├─ armor_penetration.json
│     ├─ mts_compat.json
│     └─ shell_ejection/
│        ├─ custom/
│        │  ├─ guns.json
│        │  └─ vehicle_rules.json
│        └─ generated_scan/
│           └─ superbwarfare/
│              ├─ items/
│              │  └─ ak_47.json
│              └─ vehicles/
│                 └─ ah_6.json
└─ logs/
   └─ latest.log
```

根目录下四个有固定名称的 JSON 是独立的配置入口。例如，不能把 `content_control.json` 随意拆成多个子文件；它的加载器不会递归扫描目录。

抛壳目录则不同：其下所有普通 `.json` 文件都会递归加载。推荐 `custom/` 是因为扫描输出可被重建，不是因为它具有额外优先级。外部规则 ID 会从路径生成并进行字符替换，建议文件名使用小写英文、数字和简单分隔符，减少规范化后的冲突。

## [2] 世界数据包

```text
<world>/datapacks/<pack>/
├─ pack.mcmeta
└─ data/<namespace>/
   ├─ shell_ejection/
   │  └─ rules.json
   └─ recipes/
      └─ casing_reload.json
```

数据包 `pack.mcmeta` 的版本号与抛壳文件 `format: 5` 是两回事。放在 `assets/` 下的 JSON 不是服务端抛壳数据包规则；把普通合成配方放到 `config/superbaddon/shell_ejection/`，也会因不符合 format 5 包装而被拒绝。

## [3] 生成文件与维护文件

[扫描](抛壳扫描命令)按命名空间、所属类型和注册路径组织输出。扫描器写入前会删除原有生成目录，还会删除历史单文件 `generated_scan.json`。

将需要的候选规则移到 `custom/`，精简后逐条检查 `rules[].enabled`。同一意图只保留一份长期维护的规则。任何放在 `shell_ejection/` 下的 `rules.backup.json` 仍会作为配置执行；备份应放到外面，或使用不以 `.json` 结尾的扩展名。

## [4] 客户端与服务端的职责

独立服务端的 JSON 不会自动替换客户端 JSON。涉及资源和内容的配置应随客户端整合包同步分发；玩家操控偏好保留在本地。世界数据包会随世界一起迁移，而实例 `config/` 通常会影响使用该实例的多个世界。

## [5] 仓库文档不是运行时配置

`docs/wiki/` 是同步到 GitHub Wiki 的文档源目录，不是 Minecraft 的配置目录。把实际规则放进去不会让游戏自动读取；`docs/wiki-archive/` 保存的是历史文档，也不是活动配置。
