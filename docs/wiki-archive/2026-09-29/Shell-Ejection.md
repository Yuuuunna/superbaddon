# Shell Ejection JSON Format

Shell Ejection configuration controls how superbaddon generates shell casing effects for SuperbWarfare weapons, vehicles, or ammunition.

This page only explains the **Shell Ejection JSON file format**.

It does not explain knockback rules. `/superbaddon shell_ejection scan` currently generates fields related to `target`, `ammo_override`, `ejection`, and `content_control`. It does not automatically generate knockback configuration.

---

## 1. File Source

A basic configuration file is usually generated with this command:

```text
/superbaddon shell_ejection scan
```

The scanned file is not final configuration. It is only an initial template. Pack authors should edit it according to their actual needs:

* `enabled`
* `target`
* `ammo_override`
* `ejection.by_ammo`
* `content_control`

---

## 2. Top-Level JSON Structure

A Shell Ejection JSON file is roughly made of five parts:

```json
{
  "format": 5,
  "generated_by": "superbaddon",
  "generated_at": "2026-05-30T12:34:07.264080400Z",
  "enabled_by_default": true,
  "owner_type": "vehicle",
  "owner": "superbwarfare:ah_6",
  "note": "Generated by /superbaddon shell_ejection scan.",
  "content_control": {},
  "rules": []
}
```

### Field Overview

| Field                |    Type | Purpose                                                                            |
| -------------------- | ------: | ---------------------------------------------------------------------------------- |
| `format`             |  number | Configuration format version. Current scan output uses `5`.                        |
| `generated_by`       |  string | Generator marker. Usually `superbaddon`.                                             |
| `generated_at`       |  string | Generation time. Useful for debugging where the file came from.                    |
| `enabled_by_default` | boolean | Default enabled state for rules. A rule-level `enabled` field has higher priority. |
| `owner_type`         |  string | Type of the file owner, such as `vehicle`.                                         |
| `owner`              |  string | ID of the file owner, such as `superbwarfare:ah_6`.                                |
| `note`               |  string | Human-readable note. Do not rely on it for logic.                                  |
| `content_control`    |  object | Content control rule. Used for `keep`, `recipes_only`, or `block_load`.            |
| `rules`              |   array | Actual Shell Ejection rule list.                                                   |

---

## 3. content_control

`content_control` decides whether the target content should be kept, have only its recipes disabled, or be blocked from loading.

Example:

```json
{
  "content_control": {
    "mode": "keep",
    "target_type": "vehicle",
    "target": "superbwarfare:ah_6",
    "comment": "keep this vehicle loaded"
  }
}
```

### content_control.mode

| Value          | Meaning                                                                                   |
| -------------- | ----------------------------------------------------------------------------------------- |
| `keep`         | Keep the target content. Shell Ejection rules can still apply.                            |
| `recipes_only` | Only disable or override recipes. This does not prevent registration or resource loading. |
| `block_load`   | Attempt to block the target content from loading. Used for content trimming.              |

### Important Difference

`recipes_only` is not resource trimming.

It only affects recipes or gameplay access. It does not mean resources are unloaded.

`block_load` is content-level trimming.

If you want a vehicle, item, or resource to be removed from a modpack, use `block_load`.

---

## 4. rules

`rules` is the actual array of shell ejection rules.

A file can contain multiple rules, but one rule per target is usually enough. Do not stack a dozen rules just to look “flexible”; that only makes debugging worse.

Basic structure:

```json
{
  "rules": [
    {
      "enabled": true,
      "priority": 100,
      "comment": "AH-6 shell ejection rule",
      "target": "superbwarfare:ah_6",
      "ammo_override": {},
      "ejection": {}
    }
  ]
}
```

### Rule Fields

| Field           |    Type | Purpose                                            |
| --------------- | ------: | -------------------------------------------------- |
| `enabled`       | boolean | Whether this rule is enabled.                      |
| `priority`      |  number | Rule priority. Higher value means higher priority. |
| `comment`       |  string | Human-readable note only.                          |
| `target`        |  string | Target ID affected by this rule.                   |
| `ammo_override` |  object | Ammunition override rule.                          |
| `ejection`      |  object | Main shell ejection rule body.                     |

---

## 5. ammo_override

`ammo_override` is used to restrict or replace the ammunition set allowed by the target.

Common structure:

```json
{
  "ammo_override": {
    "enabled": true,
    "policy": "replace",
    "allowed": [
      "mts:bullet_12_7x99mm",
      "mts:bullet_7_62x51mm"
    ]
  }
}
```

### ammo_override Fields

| Field     |    Type | Purpose                                 |
| --------- | ------: | --------------------------------------- |
| `enabled` | boolean | Whether ammunition override is enabled. |
| `policy`  |  string | Override policy. Commonly `replace`.    |
| `allowed` |   array | List of allowed ammunition IDs.         |

### policy: replace

`replace` means the original ammunition set is replaced by the `allowed` list.

In other words, once enabled, the target should only use ammunition listed in `allowed`.

### allowed

`allowed` contains ammunition item IDs.

Example:

```json
"allowed": [
  "mts:bullet_12_7x99mm",
  "mts:bullet_7_62x51mm"
]
```

Notes:

* IDs must actually exist.
* Typos will not fix themselves.
* If an ammo type is configured in `ejection.by_ammo` but not listed in `allowed`, the rule relationship is wrong.
* If `ammo_override.enabled = true`, then `allowed` should stay consistent with `ejection.by_ammo`.

---

## 6. ejection

`ejection` is the main shell ejection effect body.

Current core structure:

```json
{
  "ejection": {
    "by_ammo": {}
  }
}
```

`by_ammo` uses ammunition IDs as keys.

Each ammunition type can have its own casing item, count, chance, ejection port, and velocity.

---

## 7. ejection.by_ammo

Example:

```json
{
  "ejection": {
    "by_ammo": {
      "mts:bullet_12_7x99mm": {
        "mode": "drop",
        "casing": "deceasedcraft:spent_12_7x99mm_casing",
        "count": 1,
        "chance": 1.0,
        "pickup_delay": 20,
        "fallback_to_drop": true,
        "ports": [
          {
            "id": "right_port",
            "offset": [0.75, 0.35, -0.25],
            "velocity": [0.12, 0.08, 0.0],
            "random_velocity": 0.03
          }
        ]
      }
    }
  }
}
```

### by_ammo Key

The key here is the ammunition ID:

```json
"mts:bullet_12_7x99mm": {}
```

This ID should match the IDs listed in `ammo_override.allowed`.

Wrong example:

```json
"12.7mm": {}
```

This is invalid configuration.

Unless the game really has an item ID named `12.7mm`, this means nothing.

Correct example:

```json
"mts:bullet_12_7x99mm": {}
```

---

## 8. Single Ammo Ejection Entry

Each `by_ammo` entry has this structure:

```json
{
  "mode": "drop",
  "casing": "deceasedcraft:spent_12_7x99mm_casing",
  "count": 1,
  "chance": 1.0,
  "pickup_delay": 20,
  "fallback_to_drop": true,
  "ports": []
}
```

### Field Description

| Field              |    Type | Purpose                                                                  |
| ------------------ | ------: | ------------------------------------------------------------------------ |
| `mode`             |  string | Shell ejection mode. Usually keep the value generated by scan.           |
| `casing`           |  string | Item ID of the casing to generate.                                       |
| `count`            |  number | Number of casing items generated per trigger.                            |
| `chance`           |  number | Ejection chance. `1.0` means 100%.                                       |
| `pickup_delay`     |  number | Pickup delay after the casing is generated. Usually understood as ticks. |
| `fallback_to_drop` | boolean | Whether to fall back to normal dropping when no valid port is available. |
| `ports`            |   array | List of ejection ports.                                                  |

---

## 9. casing

`casing` is the item ID of the shell casing to generate.

Example:

```json
"casing": "deceasedcraft:spent_12_7x99mm_casing"
```

Notes:

* It must be a full item ID.
* It must include a namespace.
* Do not use display names.
* Do not use translation names.
* Do not use localized names.

Wrong example:

```json
"casing": "12.7mm casing"
```

Correct example:

```json
"casing": "deceasedcraft:spent_12_7x99mm_casing"
```

---

## 10. chance

`chance` controls the probability of shell ejection.

| Value | Meaning          |
| ----: | ---------------- |
| `1.0` | Always eject     |
| `0.5` | About 50% chance |
| `0.0` | Never eject      |

Recommended value:

```json
"chance": 1.0
```

Do not change this unless you explicitly want occasional missing ejections.

Random chance is not optimization. Most of the time, it only creates debugging noise.

---

## 11. count

`count` controls how many casings are generated per trigger.

Example:

```json
"count": 1
```

Do not set this to a large number casually.

Wrong example:

```json
"count": 64
```

That is not “more realistic”. That is dumping garbage entities into the server.

Recommended value:

```json
"count": 1
```

---

## 12. pickup_delay

`pickup_delay` controls how long the casing cannot be picked up after being generated.

Example:

```json
"pickup_delay": 20
```

This is usually understood as about 1 second.

Recommendations:

* Use `20` if you want casings to behave like normal drops after a short delay.
* Lower it if you want casings to be picked up almost immediately.
* Do not keep大量 casings on the ground for a long time just for visual effect.

---

## 13. fallback_to_drop

`fallback_to_drop` controls whether the rule falls back to normal dropping when no valid port is available.

Example:

```json
"fallback_to_drop": true
```

Recommended value: keep it `true`.

Reason:

If the port configuration is wrong, the item can still drop. If this is set to `false`, a bad port may cause nothing to happen at all, making debugging harder.

---

## 14. ports

`ports` is the list of shell ejection ports.

A port describes where the casing is generated and what initial velocity it receives.

Example:

```json
"ports": [
  {
    "id": "right_port",
    "offset": [0.75, 0.35, -0.25],
    "velocity": [0.12, 0.08, 0.0],
    "random_velocity": 0.03
  }
]
```

### Port Fields

| Field             |     Type | Purpose                                |
| ----------------- | -------: | -------------------------------------- |
| `id`              |   string | Port name. Useful for humans and logs. |
| `offset`          | array[3] | Spawn offset relative to the target.   |
| `velocity`        | array[3] | Initial casing velocity.               |
| `random_velocity` |   number | Extra random velocity amount.          |

---

## 15. offset

`offset` is a 3D offset array:

```json
"offset": [0.75, 0.35, -0.25]
```

Fixed format:

```text
[x, y, z]
```

Common meaning:

* `x`: left/right offset
* `y`: up/down offset
* `z`: forward/backward offset

Do not write it as an object.

Wrong example:

```json
"offset": {
  "x": 0.75,
  "y": 0.35,
  "z": -0.25
}
```

Correct example:

```json
"offset": [0.75, 0.35, -0.25]
```

---

## 16. velocity

`velocity` is the base velocity when the casing is generated:

```json
"velocity": [0.12, 0.08, 0.0]
```

The format is also:

```text
[x, y, z]
```

Do not set the velocity too high.

This is a casing, not a projectile.

---

## 17. random_velocity

`random_velocity` adds a small random disturbance to casing velocity.

Example:

```json
"random_velocity": 0.03
```

Recommended values:

|       Value | Effect                 |
| ----------: | ---------------------- |
|       `0.0` | No randomness          |
|      `0.02` | Very slight randomness |
|      `0.03` | Common value           |
|      `0.05` | Clearly scattered      |
| Above `0.1` | Usually too chaotic    |

## 19. Multiple Ammunition Example

The same target can generate different casings for different ammunition types:

```json
{
  "ejection": {
    "by_ammo": {
      "mts:bullet_12_7x99mm": {
        "mode": "drop",
        "casing": "deceasedcraft:spent_12_7x99mm_casing",
        "count": 1,
        "chance": 1.0,
        "pickup_delay": 20,
        "fallback_to_drop": true,
        "ports": [
          {
            "id": "right_port",
            "offset": [0.75, 0.35, -0.25],
            "velocity": [0.12, 0.08, 0.0],
            "random_velocity": 0.03
          }
        ]
      },
      "mts:bullet_7_62x51mm": {
        "mode": "drop",
        "casing": "deceasedcraft:spent_7_62x51mm_casing",
        "count": 1,
        "chance": 1.0,
        "pickup_delay": 20,
        "fallback_to_drop": true,
        "ports": [
          {
            "id": "right_port",
            "offset": [0.65, 0.32, -0.22],
            "velocity": [0.10, 0.07, 0.0],
            "random_velocity": 0.03
          }
        ]
      }
    }
  }
}
```

If you configure it this way, `ammo_override.allowed` should also include both ammunition types:

```json
"allowed": [
  "mts:bullet_12_7x99mm",
  "mts:bullet_7_62x51mm"
]
```

## 20. Common Mistakes

### Mistake 1: Putting knockback inside ejection

Wrong:

```json
{
  "ejection": {
    "knockback": {}
  }
}
```

Shell Ejection does not handle knockback.

Scan does not automatically generate knockback configuration either.

Knockback rules should be placed in a separate knockback configuration. Do not put them inside `ejection` or `ammo_override`.

---

### Mistake 2: by_ammo and allowed do not match

Wrong:

```json
"allowed": [
  "mts:bullet_12_7x99mm"
],
"by_ammo": {
  "mts:bullet_7_62x51mm": {}
}
```

This configuration contradicts itself.

If `ammo_override.enabled = true` and `policy = replace`, then `allowed` and `by_ammo` should at least cover the same ammunition types you intend to support.

---

### Mistake 3: Missing namespace

Wrong:

```json
"casing": "spent_12_7x99mm_casing"
```

Correct:

```json
"casing": "deceasedcraft:spent_12_7x99mm_casing"
```

Minecraft resource IDs must include a namespace.

Do not expect the loader to guess.

---

### Mistake 4: Wrong array length

Wrong:

```json
"offset": [0.75, 0.35]
```

Correct:

```json
"offset": [0.75, 0.35, -0.25]
```

Both `offset` and `velocity` must contain exactly 3 numbers.

---

### Mistake 5: Generating too many drop entities for visual effect

Wrong:

```json
"count": 16,
"chance": 1.0
```

This creates大量 entities.

If server TPS drops, do not blame Forge.

Recommended:

```json
"count": 1,
"chance": 1.0
```

---

## 21. Recommended Editing Workflow

Correct workflow:

```text
1. Run /superbaddon shell_ejection scan
2. Find the generated target JSON
3. Verify that owner_type / owner / target are correct
4. Set content_control.mode
5. Set rule.enabled
6. Set ammo_override.allowed
7. Set ejection.by_ammo
8. Check whether the casing item ID actually exists
9. Check whether offset / velocity contain exactly 3 numbers
10. Restart the game or server and test
```
